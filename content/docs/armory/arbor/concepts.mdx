Arbor models a codebase the way it actually exists in many organizations: as many repositories that depend on, reference, and compose with one another. This page explains the core ideas behind that model.

## The Polyrepo Graph

Most git providers present repositories as a flat list. Arbor instead treats your organization as a **graph**:

- **Nodes** are repositories.
- **Edges** are relationships between repositories (dependencies, references, ownership, and so on).

This makes polyrepo and microservice architectures legible. Rather than mentally reconstructing how a dozen services fit together, you see the topology directly. The graph is interactive: filter by tag, isolate a subsystem, and drill from a node into the underlying repository.

### Graph Scope and Plans

How much of that topology the graph can see depends on your plan, so the graph is a capability ladder rather than a single fixed feature:

- **Per-repository graph (Free)**: every repository gets its own dependency graph. You see the structure within a single repository, but repositories stay independent.
- **Org-wide polyrepo graph (Pro)**: the graph spans the whole organization, and [Weaver](/armory/weaver) dependency detection discovers the edges between repositories automatically, so the polyrepo topology renders as one connected view with advanced visualization.
- **Blast-radius and orchestration (Team)**: adds dependency blast-radius analysis (trace what a change to one repository affects downstream) and multi-repo Weaver orchestration across the graph.

See [Pricing](/armory/arbor/pricing) for the full ladder. Self-hosted instances run at per-repository capability by default.

## Repository Relationships

Relationships are first-class. The most common is a **dependency edge**: repository A depends on repository B. Dependency edges give the graph direction and let Arbor reason about ordering, for example "which services need to build before this one."

Other relationships capture how repositories relate beyond strict build dependencies, such as a service that consumes another's published API or schema. Edges are directional, so the graph distinguishes "depends on" from "depended on by."

### Tags

Every repository can carry tags. Tags are the primary tool for slicing a large graph into something you can reason about:

- Tag by layer: `frontend`, `backend`, `infrastructure`
- Tag by domain: `billing`, `identity`, `search`
- Tag by lifecycle: `metarepo`, `service`

Filtering the graph to a single tag collapses everything else, so a large organization graph becomes a focused view of one subsystem.

## Weaver Integration

Arbor is powered by [🕸️ Weaver](/armory/weaver), Omni's dependency-aware multi-repository orchestrator. Weaver already describes a workspace as a set of repositories with `depends_on` relationships and `tags`:

```yaml
workspace: .

repositories:
  arbor-git:
    url: git@github.com:omnidotdev/arbor-git.git
    tags: [product, backend-service, rust]

  arbor-api:
    url: git@github.com:omnidotdev/arbor-api.git
    depends_on: [arbor-git]
    tags: [product, backend]

  arbor-app:
    url: git@github.com:omnidotdev/arbor-app.git
    depends_on: [arbor-api]
    tags: [product, frontend]
```

This is the same shape as Arbor's graph: repositories, dependency edges, and tags. Arbor can ingest a Weaver workspace definition to seed the graph, so the relationships you already maintain for local development and sync become the relationships you visualize. The reverse is true as well: model a system in Arbor, and the result maps cleanly onto a Weaver workspace for orchestration.

## Services

Under the hood, Arbor is three services working together. See [Self-Hosting](/armory/arbor/self-hosting) for how to run them.

| Service | Language | Responsibility |
|---------|----------|----------------|
| `arbor-app` | TypeScript | Web UI, including the graph view |
| `arbor-api` | TypeScript | GraphQL API for organizations, repositories, and graph data |
| `arbor-git` | Rust | Git backend: storage, transport, and high-performance git operations |

The web app talks to the GraphQL API, which in turn delegates raw git storage and transport to the Rust `arbor-git` service.
