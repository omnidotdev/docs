A scheduled job runs a container on a recurring cron schedule instead of serving
traffic or running continuously. Use one for nightly data exports, periodic
cleanups, report generation, cache warming, or any task that runs on a clock.

A scheduled job is a service with **`serviceType: cronJob`** and a
**`deploy.schedule`** cron expression. It builds from the same sources as any
other service (a Git repository or a prebuilt image). On each tick it starts a
fresh container that runs the image's default command, or the job's command
override, and exits.

## Create one in the dashboard

1. Open your project and choose **Scheduled jobs** in the project header (on a
   narrow screen it is in the overflow menu).
2. Click **New scheduled job**.
3. Fill in:
   - **Name**
   - **Schedule**: a preset (every hour, every 6 hours, every day at midnight,
     every Monday) or a custom cron expression
   - **Source**: a Git repository and branch (built automatically), or a
     container image and tag
   - **Command** (optional): overrides the image's default command, for example
     `bun run cleanup`
   - **Time zone**, **Concurrency**, **Starting deadline**, **Backoff limit**,
     **Keep successful runs**, **Keep failed runs**, and a **suspend** toggle
     (see [Controls](#controls))
4. Create the job.

The form validates the schedule and time zone before the job is created.

## Manage jobs

The **Scheduled jobs** page lists every job in the project with its schedule,
time zone, concurrency policy, status, and last run. For each job you can:

- **Run now**: start a run immediately, outside the schedule. Useful for testing
  a new job or re-running after a failure.
- **Pause** and **Resume**: stop and restart the schedule without deleting the
  job. A run already in flight finishes.
- **Edit**: change the schedule, command, and controls.
- **Delete**: permanently remove the job and stop all future runs, after a
  confirmation.

Expand a job to see its run history: each run's trigger (scheduled or manual),
status, and start and completion times, retained per the history limits below.

Run now, pause, resume, run history, and each run's logs are also available
from the [CLI](#manage-jobs-from-the-cli), the [MCP server](#manage-jobs-with-the-mcp-server),
and the [API](#manage-jobs-through-the-api). All of them request a run the same
way: the platform starts the run from the job's own definition, with the same
image, command, and environment as a scheduled run, within a few seconds. A
manual run works while the schedule is paused.

A run reports one of three statuses: `Running` (pending, running, or retrying
after a failed attempt), `Succeeded`, or `Failed`. A run and its logs stay
available while it is within the job's history limits
(`successfulJobsHistoryLimit` and `failedJobsHistoryLimit`, see
[Controls](#controls)); older runs are removed.

## Manage jobs from the CLI

The [fractal CLI](/products/fractal/cli-reference#scheduled-jobs) controls
existing scheduled jobs with `fractal cron`, on both the `api` and `kube`
transports:

```bash
fractal cron list [--project <project>]         # every job: schedule, paused or active, last run
fractal cron run <service>                      # run once now; prints the run's name
fractal cron run <service> --follow             # run, stream its logs, exit non-zero unless it succeeds
fractal cron pause <service>                    # stop the schedule
fractal cron resume <service>                   # restart the schedule
fractal cron runs <service> [--limit <n>]       # recent runs, newest first
fractal cron logs <service> [--job <run>]       # a run's logs, the newest run by default
```

`fractal cron run --follow` waits for the run to finish and exits with status
`1` when it fails, so a CI pipeline can run a job (for example a migration or a
backfill) and fail the build if the job fails:

```bash
export FRACTAL_API_TOKEN="$FRACTAL_CI_TOKEN"
fractal cron run nightly-report --project acme --follow --timeout 30m
```

Running, pausing, and resuming need the `developer` role or higher on the
project; listing runs and reading logs work with any project role. The CLI does
not create jobs: create them in the dashboard or with the MCP server.

## Manage jobs with the MCP server

The [MCP server](/products/fractal/mcp) gives an AI assistant the same control:

| Tool | What it does |
|------|--------------|
| `create_cron_service` | Create a job from a Git repository or image, with a monorepo `rootDir` and `watchPaths`, a `command` override, environment variables, and optional `cron` [controls](#controls) |
| `list_cron_services` | List a project's jobs with their schedule and controls, including whether each is paused |
| `run_cron_job` | Run a job once now; returns the run's name as `job` |
| `set_cron_suspended` | Pause (`suspended: true`) or resume (`suspended: false`) the schedule |
| `list_cron_runs` | Recent runs, newest first, with status, trigger, times, and duration |
| `get_logs` | With `job`, read one run's output |

A typical assistant loop runs a job with `run_cron_job`, checks `list_cron_runs`
until that run is `Succeeded` or `Failed`, then reads its output with
`get_logs`. To change the schedule or controls of an existing job, use **Edit**
in the dashboard.

## Manage jobs through the API

Four REST endpoints on `https://api.fractal.omni.dev` cover scheduled jobs,
authenticated with an [API token](/products/fractal/api-tokens) in an
`Authorization: Bearer ftk_...` header. Each takes the job's `namespace`
(returned by the GraphQL `fractalService(project: "...", name: "...") { metadata { namespace } }`),
`project`, and `service`:

| Endpoint | Access | Parameters and response |
|----------|--------|-------------------------|
| `POST /v1/services/cron/run` | `developer` role or higher | JSON body: `namespace`, `project`, `service`. Returns `202` with `{ ok, requestedAt, job }`, where `job` is the name of the run that starts within a few seconds |
| `POST /v1/services/cron/suspend` | `developer` role or higher | JSON body: `namespace`, `project`, `service`, `suspend` (`true` pauses, `false` resumes). Returns `{ ok, suspended }` |
| `GET /v1/services/cron/runs` | Any project role | Query: `namespace`, `project`, `service`, optional `limit` (default 20, max 100). Returns `{ service, runs: [{ name, manual, status, startTime, completionTime, durationSeconds }] }`, newest first |
| `GET /v1/services/logs` | Any project role | Query: `namespace`, `project`, `service`, and `job` (a run's `name`) to read that run's output; also `tailLines`, `sinceSeconds`, `timestamps`, `previous`. Returns `{ service, namespace, pods: [{ name, container, log }] }` |

```bash
curl -X POST https://api.fractal.omni.dev/v1/services/cron/run \
  -H "Authorization: Bearer $FRACTAL_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"<namespace>","project":"<project>","service":"<service>"}'

curl -G https://api.fractal.omni.dev/v1/services/cron/runs \
  -H "Authorization: Bearer $FRACTAL_API_TOKEN" \
  -d namespace=<namespace> -d project=<project> -d service=<service> -d limit=5

curl -G https://api.fractal.omni.dev/v1/services/logs \
  -H "Authorization: Bearer $FRACTAL_API_TOKEN" \
  -d namespace=<namespace> -d project=<project> -d service=<service> -d job=<run name>
```

The cron endpoints return `400` for a service that is not a scheduled job, `404`
for a service (or run) that is not in the project, and `403` without access.
Create a job through the API with the GraphQL `createFractalService` mutation,
setting `serviceType: cronJob`, `deploy.schedule`, and optionally `deploy.cron`.

## Cron schedule syntax

`deploy.schedule` takes a standard five-field cron expression:

```
┌───────────── minute        (0-59)
│ ┌─────────── hour          (0-23)
│ │ ┌───────── day of month  (1-31)
│ │ │ ┌─────── month         (1-12 or JAN-DEC)
│ │ │ │ ┌───── day of week   (0-6 or SUN-SAT, Sunday = 0)
│ │ │ │ │
* * * * *
```

| Expression | Runs |
|------------|------|
| `*/5 * * * *` | Every 5 minutes |
| `0 * * * *` | Every hour, on the hour |
| `0 2 * * *` | Every day at 02:00 |
| `0 9 * * 1` | Every Monday at 09:00 |
| `0 0 1 * *` | At midnight on the first of each month |

Macros such as `@daily` are not accepted; use the five-field form. Schedules are
evaluated in the job's time zone (see `timeZone` below), which defaults to UTC.

## Controls

Scheduling behavior lives under **`deploy.cron`** in the service spec. Every
field is optional:

| Field | Values / default | Description |
|-------|------------------|-------------|
| `concurrencyPolicy` | `allow` (default), `forbid`, `replace` | What happens when a run is still in progress at the next tick. `allow` runs them concurrently, `forbid` skips the new run, `replace` cancels the running one and starts the new run |
| `suspend` | `false` (default) | Pause the schedule without deleting the job. No new runs start while suspended; a run already in flight finishes |
| `timeZone` | IANA name, default `UTC` | Time zone the schedule is evaluated in, for example `America/New_York` or `Europe/Oslo` |
| `startingDeadlineSeconds` | integer, optional | Deadline for starting a run if it misses its scheduled time (for example because the cluster was busy). A run that cannot start within the deadline is counted as missed and skipped |
| `successfulJobsHistoryLimit` | integer, default `3` | How many completed successful runs to keep in history |
| `failedJobsHistoryLimit` | integer, default `1` | How many failed runs to keep in history |
| `backoffLimit` | integer, default `6` | How many times a single run retries before it is marked failed |

As the service spec (what `get_service` returns), a nightly cleanup at 02:00
Europe/Oslo time that never overlaps runs looks like:

```yaml
serviceType: cronJob
source:
  git:
    url: https://github.com/acme/jobs
    branch: main
build:
  mode: auto
deploy:
  schedule: "0 2 * * *"
  command: ["bun", "run", "cleanup"]
  cron:
    concurrencyPolicy: forbid
    timeZone: Europe/Oslo
    successfulJobsHistoryLimit: 7
```

`deploy.command` is optional: without it, each run starts the image's default
command (for an auto-built Git source, the detected start command). Environment
variables, secrets, and resources work as they do for a web or worker service
(see [Service Configuration](/products/fractal/configuration)).

<Callout type="info">
Importing a [fractal.yaml](/products/fractal/configuration#fractalyaml) does not
yet carry `deploy.schedule` or `deploy.cron`. Create scheduled jobs from the
dashboard, the MCP server, or the GraphQL API.
</Callout>

## Shell access

Scheduled jobs have no **Shell** tab: there is no long-lived container to attach
to between runs (see [Shell](/products/fractal/shell)).
