A scheduled job runs a container on a recurring cron schedule instead of serving
traffic or running continuously. Use one for nightly data exports, periodic
cleanups, report generation, cache warming, or any task that runs on a clock.

A scheduled job is a service with **`serviceType: cronJob`** and a
**`deploy.schedule`** cron expression. It builds from the same sources as any
other service (a Git repository or a prebuilt image). On each tick it starts a
fresh container that runs the image's default command, or the job's command
override, and exits.

## Create one in the dashboard

1. Open your project and choose **Scheduled jobs** in the project header (on a
   narrow screen it is in the overflow menu).
2. Click **New scheduled job**.
3. Fill in:
   - **Name**
   - **Schedule**: a preset (every hour, every 6 hours, every day at midnight,
     every Monday) or a custom cron expression
   - **Source**: a Git repository and branch (built automatically), or a
     container image and tag
   - **Command** (optional): overrides the image's default command, for example
     `bun run cleanup`
   - **Time zone**, **Concurrency**, **Starting deadline**, **Backoff limit**,
     **Keep successful runs**, **Keep failed runs**, and a **suspend** toggle
     (see [Controls](#controls))
4. Create the job.

The form validates the schedule and time zone before the job is created.

## Manage jobs

The **Scheduled jobs** page lists every job in the project with its schedule,
time zone, concurrency policy, status, and last run. For each job you can:

- **Run now**: start a run immediately, outside the schedule. Useful for testing
  a new job or re-running after a failure.
- **Pause** and **Resume**: stop and restart the schedule without deleting the
  job. A run already in flight finishes.
- **Edit**: change the schedule, command, and controls.
- **Delete**: permanently remove the job and stop all future runs, after a
  confirmation.

Expand a job to see its run history: each run's trigger (scheduled or manual),
status, and start and completion times, retained per the history limits below.

## Create one with the MCP server

The [MCP server](/products/fractal/mcp)'s `create_cron_service` tool creates a
scheduled job from a Git repository or image, including a monorepo `rootDir` and
`watchPaths`, a `command` override, and environment variables. It sets the
schedule only; adjust the controls afterwards with **Edit** in the dashboard.
`list_cron_services` lists a project's jobs.

From the CLI, `fractal services` shows scheduled jobs with type `cronJob` and,
with `--json`, their `schedule`.

## Cron schedule syntax

`deploy.schedule` takes a standard five-field cron expression:

```
┌───────────── minute        (0-59)
│ ┌─────────── hour          (0-23)
│ │ ┌───────── day of month  (1-31)
│ │ │ ┌─────── month         (1-12 or JAN-DEC)
│ │ │ │ ┌───── day of week   (0-6 or SUN-SAT, Sunday = 0)
│ │ │ │ │
* * * * *
```

| Expression | Runs |
|------------|------|
| `*/5 * * * *` | Every 5 minutes |
| `0 * * * *` | Every hour, on the hour |
| `0 2 * * *` | Every day at 02:00 |
| `0 9 * * 1` | Every Monday at 09:00 |
| `0 0 1 * *` | At midnight on the first of each month |

Macros such as `@daily` are not accepted; use the five-field form. Schedules are
evaluated in the job's time zone (see `timeZone` below), which defaults to UTC.

## Controls

Scheduling behavior lives under **`deploy.cron`** in the service spec. Every
field is optional:

| Field | Values / default | Description |
|-------|------------------|-------------|
| `concurrencyPolicy` | `allow` (default), `forbid`, `replace` | What happens when a run is still in progress at the next tick. `allow` runs them concurrently, `forbid` skips the new run, `replace` cancels the running one and starts the new run |
| `suspend` | `false` (default) | Pause the schedule without deleting the job. No new runs start while suspended; a run already in flight finishes |
| `timeZone` | IANA name, default `UTC` | Time zone the schedule is evaluated in, for example `America/New_York` or `Europe/Oslo` |
| `startingDeadlineSeconds` | integer, optional | Deadline for starting a run if it misses its scheduled time (for example because the cluster was busy). A run that cannot start within the deadline is counted as missed and skipped |
| `successfulJobsHistoryLimit` | integer, default `3` | How many completed successful runs to keep in history |
| `failedJobsHistoryLimit` | integer, default `1` | How many failed runs to keep in history |
| `backoffLimit` | integer, default `6` | How many times a single run retries before it is marked failed |

As the service spec (what `get_service` returns), a nightly cleanup at 02:00
Europe/Oslo time that never overlaps runs looks like:

```yaml
serviceType: cronJob
source:
  git:
    url: https://github.com/acme/jobs
    branch: main
build:
  mode: auto
deploy:
  schedule: "0 2 * * *"
  command: ["bun", "run", "cleanup"]
  cron:
    concurrencyPolicy: forbid
    timeZone: Europe/Oslo
    successfulJobsHistoryLimit: 7
```

`deploy.command` is optional: without it, each run starts the image's default
command (for an auto-built Git source, the detected start command). Environment
variables, secrets, and resources work as they do for a web or worker service
(see [Service Configuration](/products/fractal/configuration)).

<Callout type="info">
Importing a [fractal.yaml](/products/fractal/configuration#fractalyaml) does not
yet carry `deploy.schedule` or `deploy.cron`. Create scheduled jobs from the
dashboard or the MCP server.
</Callout>

## Shell access

Scheduled jobs have no **Shell** tab: there is no long-lived container to attach
to between runs (see [Shell](/products/fractal/shell)).
