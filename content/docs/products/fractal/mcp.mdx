The Fractal MCP server exposes Fractal's deploy and operations surface to AI
assistants that speak the [Model Context Protocol](https://modelcontextprotocol.io).
Connect an MCP client (for example a coding assistant or agent) and the
assistant can list and inspect services, trigger deploys, read logs, manage
environment variables, and create, run, pause, and inspect scheduled jobs on
your workspace through typed tools.

## How it works

Fractal hosts the server at `https://mcp.fractal.omni.dev/mcp` over the
Streamable HTTP transport, so there is nothing to install. Your MCP client
authenticates every request in one of two ways:

- **Browser sign-in (default):** the client opens your browser, you sign in
  with your Omni account and approve access, and every action runs with your
  own access.
- **API token:** for CI and headless agents with no browser, the client sends a
  workspace API token (`ftk_...`), and every action runs with that token's
  access.

The server forwards the credential to the Fractal API. It stores no
credentials and keeps no sessions: each request is handled on its own.

## Connect with browser sign-in

Add the server to your client's MCP configuration as a remote (HTTP) server,
with no credentials:

```json
{
  "mcpServers": {
    "fractal": {
      "type": "http",
      "url": "https://mcp.fractal.omni.dev/mcp"
    }
  }
}
```

The first time the client connects, the server answers `401` and points the
client at Omni sign-in. The client opens your browser, you sign in, and a
consent page names the client and what it can access. Approve it, and the
client stores the sign-in and refreshes it on its own. Sign-in uses the
standard [MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
flow (OAuth 2.1 with PKCE), so any client that supports it connects without
extra setup.

An MCP client is never approved automatically: the consent page appears the
first time each client connects. Approve only a sign-in your own client
started.

## Connect with an API token

Use a token where no browser is available, such as CI jobs and headless agents.
Create a workspace API token (`ftk_...`) in the dashboard (open your workspace
and select the **API Tokens** tab) or with `fractal tokens create --name <label>`.
Copy the secret when it is shown (it is shown only once) and store it in your
MCP client's secret configuration, never in a file committed to Git. To keep an
assistant to specific projects, create a
[scoped token](/products/fractal/api-tokens#restrict-a-token-to-projects).

Pass the token in the `Authorization` header:

```json
{
  "mcpServers": {
    "fractal": {
      "type": "http",
      "url": "https://mcp.fractal.omni.dev/mcp",
      "headers": {
        "Authorization": "Bearer ftk_..."
      }
    }
  }
}
```

Clients name these fields slightly differently (some use `transport` or
`serverUrl`); the values that matter are the URL, the HTTP transport, and the
`Authorization: Bearer <token>` header.

## Workspaces

With browser sign-in, you can belong to several workspaces. The assistant
calls `list_workspaces` to see them, then passes `workspace` (the workspace's
slug or id) to the other tools to choose where to act:

- With exactly one workspace, it is selected automatically and `workspace` can
  be omitted.
- With several, a tool called without `workspace` returns an error asking the
  assistant to call `list_workspaces` and pick one.

A token is bound to the workspaces it was created for, so `workspace` does not
apply to it and is ignored.

## Tools

Tools take the project's **name** (`project`) and the service's name
(`service` or `name`). `list_projects` returns the project names. Every tool
except `list_workspaces` also takes an optional `workspace` (see
[Workspaces](#workspaces)).

| Tool | Access | Arguments | What it does |
|------|--------|-----------|--------------|
| `list_workspaces` | Read | None | List the workspaces you can act in, with each one's id, slug, name, and type |
| `list_projects` | Read | `owner`, `limit`, `offset` (all optional) | List your projects with phase and service count |
| `list_services` | Read | `project`, optional `limit`, `offset` | List a project's services with status, source, build settings, and cron schedule |
| `get_service` | Read | `project`, `name` | Read one service: phase, current image, URL, conditions and last error, source, build settings (including `rootDir` and `watchPaths`), env, and schedule |
| `list_cron_services` | Read | `project` | List only the [scheduled jobs](/products/fractal/scheduled-jobs) in a project, with each job's schedule and `deploy.cron` controls (including whether it is paused) |
| `list_cron_runs` | Read | `project`, `service`, optional `limit` (1 to 100, default 20), `namespace` | List a scheduled job's recent runs, newest first: each run's name, whether it was manual or scheduled, status (`Running`, `Succeeded`, or `Failed`), start and completion times, and duration in seconds. Any project role |
| `get_env` | Read | `project`, `service` | Read a service's environment variables. Secret-backed values are masked |
| `get_logs` | Read | `project`, `service`, optional `tailLines` (1 to 5000, default 200), `sinceSeconds`, `job` | Read a snapshot of recent logs per pod, newest pod first. Any project role can read logs. Returns no pods when the service is asleep or scaled to zero. For a scheduled job, `job` (a run's name from `run_cron_job` or `list_cron_runs`) reads that run's output |
| `deploy_service` | Write | `project`, `service`, optional `environment`, `namespace` | Rebuild and redeploy a service (the same as `fractal deploy`). Needs the `developer` role or higher. Omit `environment` to redeploy every environment |
| `set_env` | Write | `project`, `service`, `env` (list of `{ name, value }` or `{ name, secret }`), optional `replace` | Set or update environment variables. Merges with existing variables unless `replace` is `true`. A `secret` value is stored write-only in a managed secret. Triggers a rolling update |
| `create_cron_service` | Write | `project`, `name`, `schedule`, `source` (`git: { url, branch }` or `image: { repository, tag }`), optional `buildMode`, `dockerfilePath`, `rootDir`, `watchPaths`, `command`, `args`, `env`, `environment`, `cron` | Create a scheduled job from a Git repository or image. `cron` sets the [scheduling controls](/products/fractal/scheduled-jobs#controls): `concurrencyPolicy` (`allow`, `forbid`, or `replace`), `timeZone`, `suspend`, `startingDeadlineSeconds`, `successfulJobsHistoryLimit`, `failedJobsHistoryLimit`, `backoffLimit` |
| `run_cron_job` | Write | `project`, `service`, optional `namespace` | Run a scheduled job once now, outside its schedule (also while it is paused). Returns `job`, the run's name. Needs the `developer` role or higher |
| `set_cron_suspended` | Write | `project`, `service`, `suspended`, optional `namespace` | Pause (`suspended: true`) or resume (`suspended: false`) a scheduled job's schedule. A run in progress finishes. Needs the `developer` role or higher |

`get_logs` returns a snapshot, not a live stream. For a live tail, use
`fractal logs <service> --follow`.

To run a scheduled job and check the result, an assistant calls `run_cron_job`,
then `list_cron_runs` until the returned run is `Succeeded` or `Failed`, then
`get_logs` with `job` for its output. The run appears within a few seconds of
the request. A finished run's logs stay readable while the run is within the
job's history limits. To change an existing job's schedule or controls, use
**Edit** on the dashboard's **Scheduled jobs** page.

Each tool calls the same API the dashboard and [CLI](/products/fractal/cli-reference)
use, so an assistant's actions are visible and auditable the same way.

## Security

- A browser sign-in issues an access token bound to the Fractal MCP server
  (its audience), and the server refuses sign-in tokens issued for any other
  service.
- A token acts with your access across its workspace. Scope and expire tokens
  for automation, and revoke any that leak (see [API Tokens](/products/fractal/api-tokens)).
- Keep the token in your MCP client's secret store, not in a checked-in config
  file.
- Review what an assistant proposes before it runs a write tool; MCP clients
  surface each tool call for approval.
