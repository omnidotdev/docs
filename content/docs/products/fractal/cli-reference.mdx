The `fractal` CLI manages your projects and services from a terminal. It works
two ways, called transports:

- **`api`** for hosted Fractal: every command goes through the Fractal API,
  authenticated by `fractal login` or an [API token](/products/fractal/api-tokens).
  No kubeconfig is needed.
- **`kube`** for a cluster you bring yourself (BYOC) and for platform admins:
  commands talk to your cluster directly through your kubeconfig.

## Quick start (hosted)

Log in through your browser, then run commands:

```bash
fractal login                        # opens your browser to sign in

fractal services                     # every service across your projects
fractal logs <service> --follow      # follow a service's logs
fractal deploy --service <service>   # rebuild and redeploy a service
```

For CI and other non-interactive use, set `FRACTAL_API_TOKEN` to an
[API token](/products/fractal/api-tokens) instead (see
[CI and automation](#ci-and-automation)).

Services are addressed by name. When two of your projects have a service with
the same name, pick one with `--project <name-or-slug>` or `FRACTAL_PROJECT`.

## Transports

The CLI picks a transport for each command, highest precedence first:

1. The `--transport api|kube` flag.
2. The `FRACTAL_TRANSPORT` environment variable (`api` or `kube`).
3. `transport` in `~/.config/fractal/config.toml`. `fractal cluster connect`
   writes `transport = "kube"`, so a BYOC machine keeps using its own cluster
   even after an API login.
4. Otherwise `api` when a credential is configured, and `kube` when none is.

`fractal deploy` always goes through the API, and the `cluster` commands always
use your kubeconfig. Run `fractal whoami` to see which transport is active.

### Availability on hosted workspaces

| Over the API | Not available yet on hosted workspaces |
|--------------|----------------------------------------|
| `services`, `projects`, `logs`, `deploy`, `env`, `scale`, `members`, `tokens list`/`create`/`revoke`, `login`, `whoami`, `logout` | `exec`, `port-forward`, `db-connect`, `secrets-sync`, `restart`, `rollback`, `destroy`, `restore`, `canary`, `tokens delete` |

The commands in the right column exit straight away with a short message that
says what to use instead: for example, the Shell tab in the dashboard for
`exec`, or `fractal deploy` for `restart`.

## Authentication

```bash
fractal login                      # sign in through your browser
fractal login --no-browser         # print the sign-in URL and paste back the result
fractal login --token <ftk_...>    # save an API token instead (use `-` to read it from stdin)
fractal whoami                     # show who you are, your workspace, and the transport
fractal logout                     # revoke the session and clear saved credentials
```

The same commands are also available under `fractal auth` (for example,
`fractal auth login`).

### Browser login

`fractal login` runs the standard browser login flow. It opens your browser to
the Omni sign-in page; after you approve, the CLI receives the result on a
temporary `127.0.0.1` listener and saves an access token and a refresh token in
`~/.config/fractal/config.toml` (readable only by you). The access token is
refreshed silently before it expires, so you stay logged in. If the sign-in
doesn't finish within 5 minutes, the login times out; run `fractal login` again.

Over SSH, on Linux with no display, or with `--no-browser`, the CLI prints the
sign-in URL instead. Open it in any browser and approve. The browser then lands
on a `127.0.0.1` address that may fail to load: copy the full URL from the
address bar and paste it into the terminal.

When a session can no longer be refreshed, commands report
`Session expired, run fractal login`.

`fractal whoami` shows your email, name, and workspace. The workspace is the one
set in `FRACTAL_WORKSPACE`, or your only workspace when you belong to exactly
one. On the `api` transport it also checks the credential against the API and
reports how many projects it can see. Pass `--json` for the same fields as JSON.

### Credential precedence

The CLI resolves its credential in this order:

1. `FRACTAL_API_TOKEN`
2. `FRACTAL_AUTH_TOKEN` (the older name, still honored)
3. The login saved in `~/.config/fractal/config.toml` by `fractal login`

`fractal login --token` checks the token against the API before saving it.

### CI and automation

Set `FRACTAL_API_TOKEN` to an [API token](/products/fractal/api-tokens) instead
of logging in interactively. It takes precedence over any saved login. When it
is set, `fractal login` returns straight away without opening a browser, so it
is safe to call from CI:

```bash
export FRACTAL_API_TOKEN="$FRACTAL_CI_TOKEN"
fractal --json whoami   # check the token is accepted
fractal deploy --project <project> --service <service>
```

## Projects and services

```bash
fractal projects list           # list projects
fractal projects get <name>     # show a project (name or slug)

fractal services [-n, --namespace <ns>]   # list services
```

On the `api` transport, `fractal services` lists every service across your
projects; add `--project <name>` to narrow it to one. On `kube`, it lists the
services in the current kubeconfig namespace. Add `--json` for machine-readable
output with the same row shape on both transports.

### `fractal deploy`

Rebuild and redeploy an existing service (used in CI and automation).

```bash
fractal deploy --service <service> [--project <project>] [--env <environment>] [--namespace <ns>]
```

| Flag | Description |
|------|-------------|
| `--service <service>` | Service name |
| `--project <project>` | Project that owns the service. Looked up from the service name when omitted |
| `--env <environment>` | Rebuild only this environment (optional) |
| `--namespace <ns>` | Namespace the service lives in. Read from the API when omitted |

Passing both `--project` and `--namespace` skips every lookup, which suits CI.

## Logs and shell access

```bash
fractal logs <service> [--follow] [--since <dur>] [--tail <n>] [--grep <text>] \
  [--timestamps] [--previous]
fractal exec <service> [-t, --tty] [-- <command>...]
fractal port-forward <service> <local:remote>
fractal db-connect <service> [--print-only]
```

| Command | Notes |
|---------|-------|
| `logs` | `--follow` keeps tailing; `--since`, `--tail`, `--grep` filter output; `--timestamps` keeps each line's timestamp; `--previous` reads the previous (crashed) container |
| `exec` | Run a command in a service pod; `--tty` for an interactive shell. On hosted workspaces, use the Shell tab in the dashboard |
| `port-forward` | Forward a local port to the service (`8080:80` or just `8080`). Needs direct cluster access |
| `db-connect` | Open a psql session to a database service; `--print-only` prints the URL. On hosted workspaces, copy the connection string from the dashboard |

On hosted workspaces, `logs` covers up to 10 pods, newest first, and
`--follow` polls for new lines every couple of seconds. A service that is
sleeping or scaled to zero has no pods: `logs` says so instead of failing, and
`--follow` waits for it to start.

## Scaling and lifecycle

```bash
fractal scale <service> --replicas <n>
fractal restart <service>       # rolling restart
fractal rollback <service>      # roll back to the previous revision
fractal destroy <service>       # mark a service for deletion (a grace period applies)
fractal restore <service>       # restore a service that is pending deletion
```

`scale` works on every transport. `restart`, `rollback`, `destroy`, and
`restore` need the `kube` transport; on hosted workspaces, use `fractal deploy`
or the service's page in the dashboard.

## Environment variables

```bash
fractal env list <service>
fractal env set <service> KEY=VALUE [--secret]
fractal env set-secret <service> KEY --secret <secret-name> --key <secret-key>
fractal env unset <service> KEY
```

| Subcommand | Description |
|------------|-------------|
| `list` | List env vars with their source. Secret values are masked |
| `set` | Set a literal value. With `--secret` (hosted), the value is stored as a managed secret: it is sent write-only and never shown again |
| `set-secret` | Set a value from an existing secret |
| `unset` | Remove a variable |

## Canary deployments

Roll out a candidate image to a slice of traffic before promoting it. Needs the
`kube` transport; on hosted workspaces, use the service's page in the dashboard.

```bash
fractal canary start <service> --image <image> [--weight <0-100>]   # default weight: 10
fractal canary status <service>
fractal canary promote <service>   # send 100% of traffic to the candidate
fractal canary abort <service>     # revert to the primary
```

## Members

```bash
fractal members list <project>
fractal members add <project> <user> [-r, --role <role>]   # default role: developer
fractal members remove <project> <user>
```

## API tokens

Scoped tokens for automation and CI. See [API Tokens](/products/fractal/api-tokens).

```bash
fractal tokens list [--workspace <id>]
fractal tokens create --name <label> [--scope <project>]... [--expires-in-days <n>] [--workspace <id>]
fractal tokens revoke <name> [--workspace <id>]
fractal tokens delete <name>   # kube transport only; prefer revoke
```

On hosted workspaces, a token always acts as the person who creates it. After
`fractal login`, the workspace is your only workspace when you belong to exactly
one; otherwise it is inferred from your projects. Pass `--workspace <id>` (or set
`FRACTAL_WORKSPACE`) if you belong to more than one. `--subject` and
`tokens delete` need the `kube` transport.

## Cluster (BYOC)

Connect the CLI to your own cluster and manage its install tokens.

```bash
fractal cluster connect [--kubeconfig <path>] [--context <ctx>] [--name <label>] \
  [--registry <host/namespace>] [--registry-insecure]
fractal cluster status        # show the connected cluster
fractal cluster disconnect
fractal cluster list-tokens
fractal cluster revoke-token <id>
```

| Flag | Description |
|------|-------------|
| `--kubeconfig <path>` | Kubeconfig to use (defaults to `$KUBECONFIG` or `~/.kube/config`) |
| `--context <ctx>` | Kubeconfig context (defaults to the current context) |
| `--name <label>` | Human-readable cluster label shown in the dashboard |
| `--registry <host/namespace>` | Bring your own registry (e.g. `registry.example.com/myorg`) for builds and runtime images. Omit to deploy onto Omni's hosted cluster |
| `--registry-insecure` | Treat the registry as plaintext HTTP (default is HTTPS) |

`fractal cluster connect` also saves `transport = "kube"` in the CLI config, so
later commands on that machine use your kubeconfig.

### Bring your own registry (BYOC)

When you pass `--registry`, the operator pushes builds to and pulls runtime
images from your registry instead of Omni's. Your registry credential never
transits Omni: create the pull Secret yourself before applying the bundle. The
`connect` command prints the exact command, e.g.

```bash
kubectl -n fractal-system create secret docker-registry fractal-registry-credentials \
  --docker-server=registry.example.com --docker-username=<user> --docker-password=<pass>
```

## Configuration

| Variable | Purpose | Default |
|----------|---------|---------|
| `FRACTAL_API_TOKEN` | API token. Takes precedence over a saved login | unset |
| `FRACTAL_AUTH_TOKEN` | Older name for the token override | unset |
| `FRACTAL_API_URL` | Fractal API base URL | `https://api.fractal.omni.dev` |
| `FRACTAL_TRANSPORT` | `api` or `kube`; the `--transport` flag overrides it | automatic |
| `FRACTAL_PROJECT` | Default project for service commands; the `--project` flag overrides it | unset |
| `FRACTAL_WORKSPACE` | Workspace id for `tokens` commands and the workspace `whoami` shows; the `--workspace` flag overrides it | inferred |
| `FRACTAL_AUTH_URL` | Identity provider base URL for `fractal login` | `https://identity.omni.dev` |
| `KUBECONFIG` | Kubeconfig for the `kube` transport and `cluster` commands | `~/.kube/config` |

## Shell completions

fractal completions <shell>   # bash, zsh, fish, ...
