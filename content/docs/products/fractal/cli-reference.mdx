The `fractal` CLI manages your projects and services from a terminal or CI. It
works two ways, called transports:

- **`api`** for hosted Fractal: every command goes through the Fractal API at
  `https://api.fractal.omni.dev`, authenticated by `fractal login` or an
  [API token](/products/fractal/api-tokens). No kubeconfig is needed.
- **`kube`** for a cluster you bring yourself (BYOC) and for platform admins:
  commands talk to your cluster directly through your kubeconfig.

The CLI operates existing services; create new ones in the dashboard, with a
[fractal.yaml import](/products/fractal/configuration#fractalyaml), or through
the [MCP server](/products/fractal/mcp) (scheduled jobs).

## Install

Prebuilt binaries for Linux (glibc, amd64 and arm64) and macOS (Apple Silicon
and Intel) are published to
[GitHub Releases](https://github.com/omnidotdev/fractal-cli/releases), tagged
`cli-v<build-number>`. Download the one for your platform:

```bash
# Linux (amd64)
curl -sSfL https://github.com/omnidotdev/fractal-cli/releases/latest/download/fractal-linux-amd64 -o fractal

# Linux (arm64)
curl -sSfL https://github.com/omnidotdev/fractal-cli/releases/latest/download/fractal-linux-arm64 -o fractal

# macOS (Apple Silicon)
curl -sSfL https://github.com/omnidotdev/fractal-cli/releases/latest/download/fractal-darwin-arm64 -o fractal

# macOS (Intel)
curl -sSfL https://github.com/omnidotdev/fractal-cli/releases/latest/download/fractal-darwin-amd64 -o fractal

chmod +x fractal
sudo mv fractal /usr/local/bin/fractal
fractal --help
```

To pin a build, replace `latest/download` with `download/cli-v<build-number>`
(for example `download/cli-v8`). The Linux binaries link glibc, so they do not
run on musl-based distributions such as Alpine. There are no Windows binaries or
package-manager packages.

## Quick start (hosted)

Log in through your browser, then run commands:

```bash
fractal login                        # opens your browser to sign in, then picks a workspace

fractal services                     # every service across your projects
fractal logs <service> --follow      # follow a service's logs
fractal deploy --service <service>   # rebuild and redeploy a service
```

When your account belongs to several workspaces, `fractal login` asks which one
to act in; switch later with `fractal workspace use <slug>` (see
[Workspaces](#workspaces)).

For CI and other non-interactive use, set `FRACTAL_API_TOKEN` to an
[API token](/products/fractal/api-tokens) instead (see
[CI and automation](#ci-and-automation)).

Services are addressed by name. When two of your projects have a service with
the same name, pick one with `--project <name-or-slug>` or `FRACTAL_PROJECT`.

## Global options

| Option | Description |
|--------|-------------|
| `--json` | Emit JSON instead of tables. Honored by `services`, `projects list`/`get`, `whoami`, `login`, and `logs` (one metadata line, then one JSON object per log line). Other commands keep their human output |
| `--transport api\|kube` | Pick the transport for this command (see [Transports](#transports)) |
| `--project <name-or-slug>` | Project that owns the service, on the `api` transport. Falls back to `FRACTAL_PROJECT`; when neither is set, the service is looked up across your projects |
| `--workspace <slug-or-id>` | Workspace to act in for this command. Overrides `FRACTAL_WORKSPACE` and the saved workspace (see [Workspaces](#workspaces)) |

Global options can go before or after the subcommand.

## Transports

The CLI picks a transport for each command, highest precedence first:

1. The `--transport api|kube` flag.
2. The `FRACTAL_TRANSPORT` environment variable (`api` or `kube`).
3. `transport` in the CLI config file. `fractal cluster connect` writes
   `transport = "kube"`, so a BYOC machine keeps using its own cluster even
   after an API login.
4. Otherwise `api` when a credential is configured, and `kube` when none is.

`fractal deploy` always goes through the API, and the `cluster` commands always
use your kubeconfig. Run `fractal whoami` to see which transport is active. To
switch a machine back to the API after `fractal cluster connect`, pass
`--transport api`, set `FRACTAL_TRANSPORT=api`, or remove the `transport` line
from the config file.

### Availability on hosted workspaces

| Over the API | Not available on hosted workspaces |
|--------------|------------------------------------|
| `services`, `projects list`/`get`, `logs` (including `--follow`), `deploy`, `env list`/`set`/`set-secret`/`unset`, `scale`, `members list`/`add`/`remove`, `tokens list`/`create`/`revoke`, `workspace list`/`use`/`current`, `login`, `whoami`, `logout` | `exec`, `port-forward`, `db-connect`, `secrets-sync`, `restart`, `rollback`, `destroy`, `restore`, `canary`, `tokens delete` |

The commands in the right column exit straight away with a short message that
says what to use instead:

| Command | Use instead |
|---------|-------------|
| `exec` | The **Shell** tab in the dashboard |
| `restart` | `fractal deploy --service <name>` |
| `rollback`, `destroy`, `restore`, `canary` | The service's page in the dashboard |
| `db-connect` | Copy the connection string from the database's page in the dashboard |
| `secrets-sync` | `fractal env list <service>` |
| `tokens delete` | `fractal tokens revoke` (keeps an audit trail) |
| `port-forward` | No hosted equivalent; it needs direct cluster access |

## Authentication

```bash
fractal login                      # sign in through your browser
fractal login --switch-account     # sign in as a different account
fractal login --no-browser         # print the sign-in URL and paste back the result
fractal login --token <ftk_...>    # save an API token instead (use `-` to read it from stdin)
fractal whoami                     # show who you are, your workspace, and the transport
fractal logout                     # clear saved credentials (and revoke a browser session)
```

The same commands are also available under `fractal auth` (for example,
`fractal auth login`).

### Browser login

`fractal login` runs a standard OAuth sign-in (authorization code with PKCE)
against `https://identity.omni.dev`. It opens your browser to an **Authorize
Fractal CLI** page that names the account you are signed in to, so you can
confirm which account the CLI will act as (or sign in first if you are not
signed in). After you approve, the CLI receives the result on a temporary
`127.0.0.1` listener and saves an access token and a refresh token in the
[config file](#config-file). The access token is refreshed silently before it
expires, so you stay logged in. If the sign-in doesn't finish within 5 minutes,
the login times out; run `fractal login` again.

To log in as a different account than the one signed in to the browser, run
`fractal login --switch-account`. It asks you to sign in again, then shows the
**Authorize Fractal CLI** page for the account you signed in with.

When the login finishes, the terminal prints `Logged in as <email>` and the
selected workspace:

- With one workspace, the CLI selects it automatically.
- With several, the CLI shows a numbered list sorted by name and asks which to
  use. The workspace you used last is preselected (press Enter to keep it).
- With several and no terminal to ask on (for example in a script, or with
  `--json`), the CLI does not prompt. It keeps the workspace you used last when
  it is still yours, and otherwise prints how to pick one with
  `fractal workspace use <slug>`.

Over SSH, on Linux with no display, or with `--no-browser`, the CLI prints the
sign-in URL instead. Open it in any browser and approve. The browser then lands
on a `127.0.0.1` address that may fail to load: copy the full URL from the
address bar and paste it into the terminal.

When a session can no longer be refreshed, commands report
`Session expired, run fractal login`.

### `fractal whoami`

After a browser login, `whoami` shows your email, name, and the workspace
commands act in (for example `Workspace: Omni (omni)`). When no workspace is
selected and you belong to several, it says how to pick one. With an API token
it reports that an API token is in use. On the `api` transport it also checks
the credential against the API and reports how many projects it can see in the
selected workspace. `fractal --json whoami` prints the same fields
(`authenticated`, `source`, `kind`, `email`, `workspace`, `workspaceSource`,
`workspaces`, `transport`, `apiUrl`, `projects`).

### Workspaces

A browser login can belong to several workspaces. Commands act in one of them
at a time: the CLI sends the selected workspace with every API request, and the
API checks that you are a member of it.

```bash
fractal workspace list              # your workspaces; the current one is marked with *
fractal workspace use <slug-or-id>  # act in this workspace from now on
fractal workspace current           # show the workspace commands act in
```

`workspace use` checks that you belong to the workspace, then saves it in the
[config file](#config-file). `workspace list` and `workspace current` accept
`--json`.

The workspace is chosen in this order, highest precedence first:

1. The `--workspace <slug-or-id>` flag.
2. The `FRACTAL_WORKSPACE` environment variable (a slug or an id).
3. The workspace saved by `fractal login` or `fractal workspace use`.
4. Your only workspace, when you belong to exactly one.

A slug or id you do not belong to is rejected with a message pointing at
`fractal workspace list`. Workspace selection applies to browser logins only.
An [API token](/products/fractal/api-tokens) is bound to its workspaces when it
is created, so the workspace setting does not change what an API token can
access.

### `fractal logout`

`logout` clears the saved credential from the config file. For a browser login
it also revokes the session with the identity provider. A saved API token is
only removed from the machine, not revoked: revoke it with
`fractal tokens revoke` or in the dashboard. A `FRACTAL_API_TOKEN` in the
environment keeps authenticating commands after a logout.

### Credential precedence

The CLI resolves its credential in this order:

1. `FRACTAL_API_TOKEN`
2. `FRACTAL_AUTH_TOKEN` (the older name, still honored)
3. The login saved in the config file by `fractal login`

`fractal login --token` checks the token against the API before saving it.

### CI and automation

Set `FRACTAL_API_TOKEN` to an [API token](/products/fractal/api-tokens) instead
of logging in interactively. It takes precedence over any saved login. When it
is set, `fractal login` returns straight away without opening a browser, so it
is safe to call from CI:

```bash
export FRACTAL_API_TOKEN="$FRACTAL_CI_TOKEN"
fractal --json whoami   # check the token is accepted
fractal deploy --project <project> --service <service>
```

## Projects and services

```bash
fractal projects list           # list projects
fractal projects get <name>     # show a project (name or slug)

fractal services [-n, --namespace <ns>]   # list services
```

On the `api` transport, `fractal services` lists every service across your
projects; add `--project <name>` to narrow it to one. On `kube`, it lists the
services in the current kubeconfig namespace (or `--namespace`). With `--json`,
each row has `name`, `serviceType` (`web`, `worker`, `cronJob`, `staticSite`,
`database`), `phase`, `readyReplicas`, `desiredReplicas`, and `image`, plus
`rootDir`, `watchPaths`, and `schedule` when set.

### `fractal deploy`

Rebuild and redeploy an existing service from its tracked branch (or its image).

```bash
fractal deploy --service <service> [--project <project>] [--env <environment>] [--namespace <ns>]
```

| Flag | Description |
|------|-------------|
| `--service <service>` | Service name (required) |
| `--project <project>` | Project that owns the service. Looked up from the service name when omitted |
| `--env <environment>` | Rebuild only this environment (optional). Without it, every environment of the service redeploys |
| `--namespace <ns>` | Namespace the service lives in. Read from the API when omitted |

Passing both `--project` and `--namespace` skips every lookup, which suits CI.
Deploying needs the `developer` role or higher on the project.

## Logs and shell access

```bash
fractal logs <service> [-f, --follow] [--since <dur>] [-t, --tail <n>] [-g, --grep <text>] \
  [--timestamps] [--previous]
fractal exec <service> [-t, --tty] [-- <command>...]
fractal port-forward <service> <local:remote>
fractal db-connect <service> [--print-only]
fractal secrets-sync <service> [-o, --output <path>] [--overwrite]
```

| Command | Notes |
|---------|-------|
| `logs` | `--follow` keeps tailing; `--since` takes `30s`, `5m`, `1h`, or `2d`; `--tail` limits lines per pod; `--grep` keeps lines containing the text; `--timestamps` keeps each line's timestamp; `--previous` reads the previous (crashed) container |
| `exec` | Run a command in a service pod (default `/bin/sh`); `--tty` for an interactive shell. `kube` only |
| `port-forward` | Forward a local port to the service (`8080:80` or just `8080`). `kube` only |
| `db-connect` | Open a `psql` session to a database service; `--print-only` prints the connection details. `kube` only |
| `secrets-sync` | Write a service's env vars into a local `.env` file (default `./.env`). `kube` only |

On hosted workspaces, `logs` reads up to 10 pods, newest first, with 200 lines
per pod by default (`--tail` accepts up to 5000). `--follow` polls for new lines
every 2 seconds and stops after 5 failed polls in a row. A service that is
sleeping or scaled to zero has no pods: `logs` says so instead of failing, and
`--follow` waits for it to start. Any project role, `viewer` included, can read
logs.

## Scaling and lifecycle

```bash
fractal scale <service> -r, --replicas <n>
fractal restart <service>       # rolling restart
fractal rollback <service>      # roll back to the previous revision
fractal destroy <service>       # mark a service for deletion (a grace period applies)
fractal restore <service>       # restore a service that is pending deletion
```

`scale` works on every transport. `restart`, `rollback`, `destroy`, and
`restore` need the `kube` transport; on hosted workspaces, use `fractal deploy`
or the service's page in the dashboard.

## Environment variables

```bash
fractal env list <service>
fractal env set <service> KEY=VALUE [--secret]
fractal env set-secret <service> KEY --secret <secret-name> --key <secret-key>
fractal env unset <service> KEY
```

| Subcommand | Description |
|------------|-------------|
| `list` | List env vars with their source. Secret values are masked |
| `set` | Set a literal value. With `--secret` (hosted only), the value is stored as a managed secret: it is sent write-only and never shown again |
| `set-secret` | Set a value from an existing secret, such as a database's `<name>-app` secret |
| `unset` | Remove a variable |

## Canary deployments

Roll out a candidate image to a slice of traffic before promoting it. Needs the
`kube` transport; on hosted workspaces, use the service's page in the dashboard.

```bash
fractal canary start <service> --image <image> [--weight <0-100>]   # default weight: 10
fractal canary status <service>
fractal canary promote <service>   # send 100% of traffic to the candidate
fractal canary abort <service>     # revert to the primary
```

## Members

```bash
fractal members list <project>
fractal members add <project> <user> [-r, --role <role>]   # default role: developer
fractal members remove <project> <user>
```

`<user>` is a user id or email. Roles are `admin`, `developer`, and `viewer`.
The project owner cannot be removed.

## API tokens

Tokens for automation and CI. See [API Tokens](/products/fractal/api-tokens).

```bash
fractal tokens list
fractal tokens create --name <label> [--scope <project>]... [--expires-in-days <n>]
fractal tokens revoke <name>
fractal tokens delete <name>   # kube transport only; prefer revoke
```

| Flag | Description |
|------|-------------|
| `--name <label>` | Label for the token (for example `github-actions-ci`) |
| `--scope <project>` | Restrict the token to a project, by its name from `fractal projects list` (not its slug). Repeat for several projects. Omit (or pass `*`) for every project you can access |
| `--expires-in-days <n>` | Lifetime in days. Omit for a non-expiring token |

`tokens create` prints the secret once; copy it then. `tokens revoke` revokes
the newest active token with that label. On hosted workspaces, a token always
acts as the person who creates it. Tokens belong to the workspace commands act
in (see [Workspaces](#workspaces)): the global `--workspace` flag,
`FRACTAL_WORKSPACE`, or the saved workspace. With none of those set, it falls
back to the workspace that owns your projects. With an API token, pass the
workspace id. `--subject` and `tokens delete` need the `kube` transport.

## Cluster (BYOC)

Connect the CLI to your own cluster and manage its install tokens. See
[Self-hosting (BYOC)](/products/fractal/self-hosting).

```bash
fractal cluster connect [--kubeconfig <path>] [--context <ctx>] [--name <label>] \
  [--registry <host/namespace>] [--registry-insecure]
fractal cluster status        # check the operator is installed and ready
fractal cluster disconnect    # print how to stop the operator
fractal cluster list-tokens   # install tokens you have issued
fractal cluster revoke-token <id>
```

| Flag | Description |
|------|-------------|
| `--kubeconfig <path>` | Kubeconfig to use (defaults to `$KUBECONFIG` or `~/.kube/config`) |
| `--context <ctx>` | Kubeconfig context (defaults to the current context) |
| `--name <label>` | Human-readable cluster label shown in the dashboard |
| `--registry <host/namespace>` | Bring your own registry (for example `registry.example.com/myorg`) for builds and runtime images. Omit to use Omni's registry |
| `--registry-insecure` | Treat the registry as plaintext HTTP (default is HTTPS) |

`fractal cluster connect` also saves `transport = "kube"` in the CLI config, so
later commands on that machine use your kubeconfig.

### Bring your own registry (BYOC)

When you pass `--registry`, the operator pushes builds to and pulls runtime
images from your registry instead of Omni's. Your registry credential never
transits Omni: create the pull Secret yourself before applying the bundle. The
`connect` command prints the exact command, for example:

```bash
kubectl -n fractal-system create secret docker-registry fractal-registry-credentials \
  --docker-server=registry.example.com --docker-username=<user> --docker-password=<pass>
```

## Configuration

### Environment variables

| Variable | Purpose | Default |
|----------|---------|---------|
| `FRACTAL_API_TOKEN` | API token (`ftk_...`). Takes precedence over a saved login | unset |
| `FRACTAL_AUTH_TOKEN` | Older name for the token override | unset |
| `FRACTAL_API_URL` | Fractal API base URL. Overrides `api_url` in the config file | `https://api.fractal.omni.dev` |
| `FRACTAL_TRANSPORT` | `api` or `kube`; the `--transport` flag overrides it | automatic |
| `FRACTAL_PROJECT` | Default project for service commands; the `--project` flag overrides it | unset |
| `FRACTAL_WORKSPACE` | Workspace to act in (slug or id). Overrides the saved workspace; the `--workspace` flag overrides it (see [Workspaces](#workspaces)) | saved workspace |
| `FRACTAL_AUTH_URL` | Identity provider base URL for `fractal login` | `https://identity.omni.dev` |
| `KUBECONFIG` | Kubeconfig for the `kube` transport and `cluster` commands | `~/.kube/config` |

### Config file

`fractal login` and `fractal cluster connect` write `fractal/config.toml` in
your user config directory: `$XDG_CONFIG_HOME/fractal/config.toml` (usually
`~/.config/fractal/config.toml`) on Linux, and
`~/Library/Application Support/fractal/config.toml` on macOS. It is readable
only by you. Besides the saved credential, it can hold `transport = "api"` or
`"kube"` and `api_url = "..."` at the top level, and a `[workspace]` table with
the workspace selected by `fractal login` or `fractal workspace use`.

## Shell completions

```bash
fractal completions <shell>   # bash, zsh, fish, elvish, powershell
```

For example, `fractal completions zsh > ~/.zfunc/_fractal`.
