A service is configured through the dashboard (the create form and the
**Settings** tab), a [fractal.yaml import](#fractalyaml), or the Fractal
[API](/products/fractal/api-tokens#http-api). The fields below are the service
spec; keys use `camelCase`. `fractal --json services` and the MCP `get_service`
tool read them back.

## Source

Every service builds from a Git repository or runs a prebuilt image.

- **Git**: repository `url` and `branch`. Fractal builds the image in-cluster on
  every push (automatic language detection, or a `Dockerfile` in the repo).
- **Image**: `repository` and `tag` of a container image to run directly.

## Build

`build.mode` controls how a Git source is built:

| Mode | Behavior |
|------|----------|
| `auto` | Detect the language and generate an optimized build (default) |
| `dockerfile` | Build from a `Dockerfile` in the repo |
| `none` | No build step (image sources) |

Additional build settings:

| Field | Applies to | Description |
|-------|------------|-------------|
| `rootDir` | all | Build subdirectory for a monorepo (for example `apps/web`). The build runs from here instead of the repository root. Default: repository root |
| `watchPaths` | all | Path prefixes (relative to the repo root) that scope monorepo rebuilds: a push rebuilds this service only when a changed file is under one of them. Default: rebuild on any change. See [Watch paths](/products/fractal/monorepos#watch-paths) |
| `dockerfilePath` | `dockerfile` | Path to the `Dockerfile`, relative to the build context (`rootDir` when set, otherwise the repository root; default `Dockerfile`) |
| `args` | `dockerfile` | Build arguments (for example `VITE_*` values needed at build time) |
| `resources` | all | CPU and memory for the build pod (defaults: 1 CPU, 2Gi) |
| `timeoutSeconds` | all | Maximum build time (default 1200) |
| `packageManager` | `auto` | Override the detected package manager (`npm`, `pnpm`, `yarn`, `bun`) |
| `installCommand` | `auto` | Override the dependency install command |
| `buildCommand` | `auto` | Override the build command |
| `startCommand` | `auto` | Override the runtime start command (a single string, for example `"bun run start"`) |

### Monorepos

Several apps in one repository deploy as separate services on the same
repository and branch. Set `rootDir` to the app's directory and, optionally,
`watchPaths` to the paths whose changes should rebuild it. See
[Monorepos](/products/fractal/monorepos) for the build behavior, the matching
rules, and when Fractal rebuilds anyway.

## Deploy

| Field | Description |
|-------|-------------|
| `replicas` | Desired replica count |
| `command` | Container command as a list, overriding the image's entrypoint |
| `args` | Container arguments as a list, overriding the image's default arguments |
| `env` | Environment variables (literal values or Secret references) |
| `resources` | CPU and memory requests/limits |
| `volumes` | Persistent volumes (see below) |
| `healthCheck` | HTTP path used for liveness/readiness |
| `sleep` | Pause the service (scale to 0) |
| `autoscale` | Autoscaling policy (see below) |
| `release` | Pre-deploy command run before a new version takes traffic (see below) |
| `requiredEnv` | Names of env vars the service must have (see below) |
| `schedule`, `cron` | Cron schedule and scheduling controls for a `cronJob` service (see [Scheduled Jobs](/products/fractal/scheduled-jobs)) |

### Release command

Run a command once per deploy **before** the new version takes traffic. This is
the place for database migrations: the command runs on the freshly built image,
with the same environment and secrets as the app, and the rollout is gated on it
succeeding.

- On **success**, the new image is promoted normally.
- On **failure**, the new version is **not** promoted and the previous healthy
  version keeps serving. The failure and the command's log output are shown on
  the service, so nobody has to run migrations against production by hand.

It runs once per deploy (not once per replica), so migrations never race across
instances.

| Field | Description |
|-------|-------------|
| `command` | The command to run, as a list (for example `["bun", "db:migrate"]`) |
| `timeoutSeconds` | Max run time before the release is failed (default 600) |

```yaml
deploy:
  release:
    command: ["bun", "db:migrate"]
    timeoutSeconds: 300
```

Release commands apply to web and worker services. A rollback reuses an
already-released image, so it does not re-run the release command.

<Callout type="info">
On hosted workspaces, the release command is not yet settable from the
dashboard, the API, or a fractal.yaml import. On a
[BYOC cluster](/products/fractal/self-hosting), set `spec.deploy.release` on the
`FractalService` resource directly.
</Callout>

### Environment variables

Each variable is either a literal value or a reference to a stored secret. In the
dashboard use the **Variables** tab; from the CLI:

```bash
fractal env set my-api NODE_ENV=production
fractal env set-secret my-api DATABASE_URL --secret main-db-app --key uri
```

#### Required environment variables

List the env vars your service cannot run without in `requiredEnv`, from the
**Required environment** field in the service's **Settings** tab (one name per
line). When any are missing from `env`, the service surfaces a **`RequiredEnv`**
condition naming the absent variables, so a deploy that would crash on missing
config is flagged with the specific cause up front. The check is advisory: it
does not block the deploy.

```yaml
deploy:
  requiredEnv:
    - DATABASE_URL
    - BETTER_AUTH_SECRET
```

If a service does crash anyway, its status shows the failure reason (for
example `CrashLoopBackOff` or the exit code) and a recent slice of the container
logs, so you can see why without digging through the cluster.

### Volumes

Attach persistent storage with a mount path, size, and optional storage class:

| Field | Example |
|-------|---------|
| `mountPath` | `/var/lib/data` |
| `size` | `10Gi` |
| `storageClass` | cluster default if omitted |

Volume size can be increased but not shrunk. The dashboard shows live disk usage
per volume so you can see how full each one is.

### Autoscaling

The default policy is a CPU-based Horizontal Pod Autoscaler:

| Field | Description |
|-------|-------------|
| `minReplicas` | Lower bound |
| `maxReplicas` | Upper bound |
| `targetCpuPercent` | Target average CPU (default 80) |

#### Scale to zero

Set `scaleToZero: true` for request-driven scale-to-zero: idle services scale to
**0** and wake automatically on the first HTTP request. This trades a small cold
start on the first request for zero idle cost.

| Field | Description |
|-------|-------------|
| `scaleToZero` | Enable request-driven scale-to-zero |
| `idleTimeoutSeconds` | Idle window before sleeping (default 300) |

Scale-to-zero requires an exposed HTTP port (traffic is what wakes the service).

## Expose

Network exposure is optional. When set, Fractal routes public traffic to your
service and provisions TLS automatically.

| Field | Description |
|-------|-------------|
| `port` | Port the service listens on |
| `domain` | Custom domain (see [Custom Domains](/products/fractal/custom-domains)) |
| `tls` | Enable TLS |
| `www` | `redirect` to send `www.` to the apex, or `off` |

## Service types

| Type | Description |
|------|-------------|
| `web` | HTTP-serving web application (default) |
| `worker` | Background worker process |
| `cronJob` | Scheduled job (with a cron schedule) |
| `staticSite` | Static site (HTML/CSS/JS) |
| `database` | Managed Postgres database |

## Databases

A database is a service with `serviceType: database`. Fractal provisions a managed
Postgres database with a connection pooler and stores the connection
credentials in a secret named `<database>-app`. Reference that secret from
another service (here for a database named `main-db`):

```bash
fractal env set-secret api DATABASE_URL --secret main-db-app --key uri
```

The dashboard's **Database** option also offers Valkey, Redis, MySQL, and
MongoDB. These run as image-based worker services on a persistent volume,
reachable inside the project at `<name>:<port>`. They are not managed: no
connection pooler, automatic backups, or high availability.

Backups are enabled by default and managed from the **Backups** tab. See
[Backups](/products/fractal/backups) for scheduled backups, on-demand backups, and
restores.

## fractal.yaml

A `fractal.yaml` describes a project's services in one file. To use one, open
the project, choose **Import**, and pick **Fractal Config**. Paste or upload the
file, or load it from the root of a connected GitHub repository
(`fractal.yaml`, then `fractal.yml`). Review the parsed services and import
them. The project's **Export** action writes the current services back out as a
`fractal.yaml`.

Import is a one-time create: it adds the listed services to the project.
Later commits to the file in the repository are not synced to the services.

`services` is a map keyed by service name:

```yaml
version: "1"
services:
  api:
    source:
      git:
        url: https://github.com/acme/api
        branch: main          # default: master
    build:
      mode: auto              # auto | dockerfile | none
    serviceType: web          # web | worker | staticSite
    deploy:
      replicas: 2
      env:
        - name: NODE_ENV
          value: production
        - name: DATABASE_URL
          valueFrom:
            secretRef:
              name: main-db-app
              key: uri
      resources:
        cpu: 500m
        memory: 512Mi
      healthCheck:
        path: /health
    expose:
      port: 3000
      domain: api.example.com
      www: "off"              # "off" | redirect
  cache:
    source:
      image:
        repository: valkey/valkey
        tag: 8-alpine         # default: latest
```

An import applies these fields:

| Section | Fields |
|---------|--------|
| `source` | `git` (`url`, `branch`) or `image` (`repository`, `tag`) |
| `build` | `mode`, `dockerfilePath`, `rootDir`, `watchPaths` |
| `serviceType` | `web`, `worker`, `staticSite`. Defaults to `web` when `expose` is set, otherwise `worker` |
| `deploy` | `replicas`, `env` (literal `value` or `valueFrom.secretRef`), `resources`, `healthCheck`, `volumes` |
| `expose` | `port`, `domain`, `tls`, `www` |

Keep secret values out of the file: reference a secret with
`valueFrom.secretRef` instead. Other settings, including `deploy.release`,
`deploy.requiredEnv`, `deploy.schedule`, and `deploy.cron`, are not applied by
an import; set them on the service afterwards (see
[Scheduled Jobs](/products/fractal/scheduled-jobs) for cron services). An unknown
`build.mode` or `serviceType` produces a warning in the import preview and falls
back to the default.
