Alongside transactional mail, Herald sends marketing broadcasts to audiences of contacts. Broadcasts ship with one-click unsubscribe and CAN-SPAM compliant footers built in.

## Audiences

An audience is a named list of contacts you can broadcast to, such as an "Omni Clients" list. You can build an audience directly in Herald or keep one in sync from an external source.

### Sync from Mantle

Populate a Herald audience from the Mantle CRM (external, email-consented contacts) and keep it reconciled. The sync is idempotent and re-runnable.

```bash
# mint an automation API key (needs an existing full key or a Gatekeeper JWT)
HERALD_API_KEY=hk_existing_full bun apikey:create

# preview what would sync (and, with --prune, what would be removed)
MANTLE_SERVICE_KEY=... HERALD_API_KEY=hk_... bun audience:sync-mantle --dry-run --prune

# sync and reconcile into the "Omni Clients" audience
MANTLE_SERVICE_KEY=... HERALD_API_KEY=hk_... bun audience:sync-mantle --prune
```

- `--dry-run` previews changes without applying them.
- `--all-emails` adds every consented address for a contact; the default is the primary only.
- `--prune` removes subscribed contacts no longer present in Mantle, and never touches contacts that have unsubscribed.

<Callout type="info">
  Only email-consented contacts sync, and pruning leaves unsubscribed contacts alone, so an audience always reflects current consent.
</Callout>

## Compliance

Every broadcast carries the pieces that keep marketing mail compliant:

- **One-click unsubscribe** so recipients can opt out in a single action.
- **CAN-SPAM compliant footers** included automatically.

Unsubscribes and complaints feed Herald's suppression list, so a contact who opts out or reports a message is not sent to again. See [Deliverability](/products/herald/deliverability) for how suppression protects your sending reputation.

### Set your sender identity first

Marketing compliance needs a sender name and a physical postal address. Set both in the dashboard under Settings before sending; a marketing send is refused until they are present, so bulk mail never goes out without them. These values only apply to marketing mail, so transactional sends are unaffected.

## Branded broadcasts

Broadcasts are written in the dashboard's [editor](/products/herald/broadcasts#write-a-broadcast) and, once a workspace admin sets up a [brand kit](/products/herald/brand), wrapped in an email-safe branded layout with your logo, colors, font, and footer note. Every broadcast is [approved](/products/herald/broadcasts#approve-a-broadcast) by an owner or admin before it sends, and the approval pins the brand kit to it.

### Body format

A broadcast's `bodyFormat` decides how its body is treated:

- `rich`: the editor's HTML. Herald sanitizes it on save (only formatting, links, and images uploaded to the workspace are kept), wraps it in the branded layout when that is on, and writes the plain-text version when none is given.
- `html`: raw markup sent exactly as written, without the branded layout.

Dashboard users write `rich` bodies by default; API keys default to `html`. Workspace members can't choose `html` (the API refuses with `HTML_BODY_FORBIDDEN`), so only owners, admins, and API keys send custom HTML. A `rich` body with an image that isn't one of the workspace's uploads is refused with `IMAGE_NOT_HOSTED`, and an unsupported or unclosed personalization tag with `INVALID_MERGE_TAGS`. Content that is too long, or has too many personalization tags, is refused with `CONTENT_TOO_LARGE`.

### Preheader

A broadcast's optional `preheader` (up to 250 characters) is the inbox preview text shown after the subject. It applies to `rich` bodies, where Herald places it hidden at the top of the email, and may use personalization tags like the subject.

## One-off marketing sends

Broadcasts are the usual way to reach an audience, but a single send can opt into the same compliance treatment. Pass `marketing: true` and Herald adds the one-click `List-Unsubscribe` header and the CAN-SPAM footer (unsubscribe link, sender name, and postal address), exactly as it does for a broadcast:

```ts
await herald.emails.send({
  from: "news@yourdomain.com",
  to: "subscriber@example.com",
  subject: "October product update",
  html: "<p>What's new this month</p>",
  marketing: true,
});
```

The same flag works on `sendBatch` and on the REST `/messages` endpoint. A marketing send is refused with a clear error until the sender identity above is set, so a one-off campaign never ships without an opt-out. Omit the flag for transactional mail, which stays byte-for-byte unchanged.
