## Overview

Taproot delegates authorization to Postgres Row-Level Security (RLS). Instead of checking permissions in application code, the database enforces access rules.

Each GraphQL request runs inside a Postgres transaction with `SET LOCAL` statements that set the role and JWT claims. RLS policies then filter rows based on these settings.

## Configuration

```yaml
auth:
  rls: true
  role_claim: "pg_role"           # JWT claim -> SET LOCAL ROLE
  claims_setting: "request.jwt.claims"  # Postgres setting name for claims
  default_role: "anonymous"       # Role when no JWT is present
  jwt_secret: "your-secret"       # Optional: verify JWT signatures (HS256)
```

## How it works

1. Client sends a request with `Authorization: Bearer <jwt>`
2. Taproot decodes the JWT and extracts claims
3. Before executing SQL, Taproot runs in a transaction:
   ```sql
   SET LOCAL ROLE 'authenticated';
   SET LOCAL "request.jwt.claims" = '{"sub":"user-123","org_id":"org-456"}';
   -- Query executes here, RLS policies are active
   COMMIT;
   ```
4. Postgres RLS policies reference the claims:
   ```sql
   CREATE POLICY user_isolation ON users
     FOR SELECT USING (
       id::text = current_setting('request.jwt.claims', true)::jsonb->>'sub'
     );
   ```

## Setting up RLS

### 1. Enable RLS on tables

```sql
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE users FORCE ROW LEVEL SECURITY;
```

### 2. Create a role for authenticated users

```sql
CREATE ROLE authenticated NOLOGIN;
GRANT USAGE ON SCHEMA public TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO authenticated;
```

### 3. Create policies

```sql
-- Users can only see their own row
CREATE POLICY user_own_row ON users
  FOR SELECT USING (
    id::text = current_setting('request.jwt.claims', true)::jsonb->>'sub'
  );

-- Users can only see posts by users in their org
CREATE POLICY org_posts ON posts
  FOR SELECT USING (
    author_id IN (
      SELECT id FROM users
      WHERE org_id = current_setting('request.jwt.claims', true)::jsonb->>'org_id'
    )
  );
```

### 4. Configure Taproot

Set `auth.rls: true` and include the `pg_role` claim in your JWT:

```json
{
  "sub": "user-123",
  "org_id": "org-456",
  "pg_role": "authenticated"
}
```

## JWT verification

If `auth.jwt_secret` is set, Taproot verifies JWT signatures using HS256. If not set, tokens are decoded without verification (useful when a gateway handles verification upstream).

## Connection pooling

The role and claims are applied with `SET LOCAL`, which is scoped to the current transaction rather than the session. When the transaction ends, on commit or rollback (including the implicit rollback when a request fails), Postgres discards both settings automatically.

This is what keeps the identity boundary intact behind a connection pooler. Each request opens its own transaction, applies its `SET LOCAL ROLE` and claims, runs its queries, and ends the transaction before the connection is returned to the pool. The next request to borrow that connection sees no residual role or claims, so there is nothing to reset and no way for one user's context to leak into another's. A session-level `SET` would not have this property, which is why Taproot never uses one.

Because the guarantee comes from transaction scoping, it holds regardless of how connections are managed, including an external pooler running in transaction mode.

## RLS with subscriptions

Subscription queries also respect RLS. The `SET LOCAL` statements are applied before fetching the changed row, so users only receive notifications for rows they can access.
